# Пул узлов для routing, поиска и сборщика

`GONKA_NODES_FILE=config/nodes.json` — JSON-конфиг с массивом `nodes` из 1–64
доверенных HTTP(S) origins. В репозитории задано 10 endpoint. Альтернативные
порты node1/node2 и публичные gateway могут использовать общие backend-ноды:
это не гарантия десяти независимых источников. В Docker конфиг включён в образ
и выбран по умолчанию; его изменение требует перезапуска/деплоя.

Файл имеет приоритет над `GONKA_NODE_URLS` и legacy-переменными. Некорректный
или отсутствующий явно заданный файл останавливает запуск без тихого fallback.
Альтернатива без файла — список через запятую:

```dotenv
GONKA_NODE_URLS=https://node1.gonka.ai:8443,https://node3.gonka.ai
```

REST `/chain-api` и RPC `/chain-rpc` строятся от одного origin. Пути, credentials,
query, fragments и дубли запрещены; пустая настройка останавливает запуск.
Адреса задаёт оператор, никогда HTTP-клиент. Редиректы отключены. Список не
обновляется автоматически из реестра участников: обнаруженный узел ещё не
является проверенным источником истории контрактов.

Настройка пула имеет приоритет над `GONKA_REST_URL` / `GONKA_RPC_URL`. Если
заданы только прежние переменные, сохраняется прежний режим одного узла без
пула. Если ни одна настройка не задана, используются node1:8443 и node3:443.
Workflow деплоя выбирает `/app/config/nodes.json` после merge в main; создание PR ничего
в Cloud Run не меняет. Для отката к одному узлу задайте список из одного origin
либо удалите `GONKA_NODES_FILE` и `GONKA_NODE_URLS` и восстановите legacy-переменные.

## Выбор и исключение узлов

Поиск и сборщик делят состояние индексируемых запросов в пределах одного
процесса. Routing использует тот же inventory, но отдельную оценку здоровья:
ему не нужен tx_index, и ошибка tx_search не исключает ноду для routing. Сначала
выбирается узел с меньшим числом наших активных операций, затем — с меньшим
сглаженным временем завершения операции. Это оценка наблюдаемого обслуживания,
не измерение CPU чужого сервера. Время зависит также от размера поиска/снимка.

Перед каждой попыткой проверяется `/status`: `gonka-mainnet`, положительная
высота, `catching_up=false`, `tx_index=on`, возраст блока менее 180 секунд
(включая допустимое отклонение часов в будущее). Проверка status не доказывает
полноту истории: реальные REST/RPC-ошибки также прерывают попытку. Узел без
индекса непригоден и для полного сборщика, которому нужна история событий.

Неуспешная попытка исключает узел на 30 секунд. По истечении паузы допускается
одна пробная операция; нет фонового потока проверок и бесконечных повторов.
Отмена освобождает счётчик активности. Успех старой параллельной операции не
снимает более позднее исключение. Лог `pool.node / cooldown` содержит
`node_index` — индекс в настроенном списке с нуля, без URL и данных запросов.

## Границы повторов и согласованность

Новый поиск пробует каждый подходящий узел не более одного раза, до 12 секунд на
попытку, в прежнем общем бюджете 30 секунд. На попытку сохраняется лимит
256 запросов поиска/деталей и 1000 событий; добавляется проверка status пула.
Повтор начинается с исходных фильтров: результаты неудачной попытки отбрасываются.
Лимит 8 одновременных поисков относится ко всему запросу, включая повторы.

Курсор закрепляет источник истории (origin), высоту и позицию. Продолжение
использует тот же узел независимо от балансировки. Если он недоступен — 503;
клиент может начать поиск заново без курсора. Старые курсоры без источника и
курсоры удалённого из конфигурации узла — 400 `INVALID_CURSOR`. Legacy-режим
также отвергает курсоры пула. Поэтому при переходе режима нужен новый поиск.
Курсор не подписан; содержащийся в нём адрес только сопоставляется с allowlist,
никогда не становится произвольным сетевым URL.

Сборщик повторяет **весь** снимок, каждый подходящий узел не более одного раза, до 20 секунд
на попытку и с прежним общим бюджетом refresh 50 секунд. Данные и история
разных попыток не смешиваются. Если все попытки провалены, прежний кэш
остаётся `stale`; частичный снимок не публикуется. Бюджеты отдельных попыток
могут прерывать медленный, но работающий узел раньше прежнего общего таймаута.

REST config/state остаются текущими значениями, не атомарным снимком на
`search_height`. Наличие индекса не гарантирует полноты: поле
`history_completeness=unknown` сохраняется.

`/v1/deals/{deal}/routing` использует тот же список. Одна попытка занимает до
3 секунд, общий deadline сохраняется: 12 секунд на весь запрос. При HTTP,
transport, JSON, stale/wrong-chain ошибке или несогласованном наблюдении вся
проверка начинается на следующем узле: status, epoch, identity, registration,
recipient, epoch, status. Частичные данные не переносятся. Каждый кандидат
пробуется не более одного раза; общий deadline может закончиться раньше конца
списка. Epoch retry остаётся внутри попытки. Evidence содержит фактически
успешный origin. Chain ID и pins контрактов не меняются; DealMismatch,
DealUnregistered и RoutingInvalid возвращаются сразу без попытки найти другой
результат на другой ноде. Лимит 8 наблюдений и отмена действуют на весь запрос.
В legacy-режиме routing сохраняет исходную закреплённую ноду.

## Проверка всех типов запросов

```sh
python3 scripts/probe_nodes.py config/nodes.json --output /tmp/node-report.json
```

Утилита выполняет только GET, до 8 узлов параллельно. Проверяет status, epoch,
ContractInfo, config, state, registry, registration, recipient, tx_search для
истории и поиска. `--deal` выбирает сделку, `--timeout` — таймаут одного запроса.
Отчёт содержит статус, категорию ошибки и длительность, без тела ответа.
Регистрация и recipient пропускаются с явным `config_unavailable`, если config
не получен. Это диагностическая матрица HTTP/JSON, не замена проверки pins в Rust.
Реальные запросы сервиса продолжают определять здоровье узлов и cooldown.

[Локальный замер 01.11.2026](research/node-probe-2026-11-01.json): все 10 endpoint
ответили на routing-запросы; оба порта node2 имеют tx_index=off и дают 500 на
tx_search. Остальные 8 endpoint ответили на все проверенные запросы. Доступность
из Cloud Run этим замером не подтверждается. Исходный список genesis origins:
[официальный FAQ](https://gonka.ai/docs/FAQ/); gateway:
[документация rpc.gonka.gg](https://rpc.gonka.gg/endpoints) и
[GNS](https://gonka.gg/names/docs). Наличие адреса в inference participants само
по себе не означает доступность chain-api/chain-rpc (многие возвращают 404).
