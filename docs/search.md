# Прямой поиск Forward в сети

`POST /v2/deals/search` выполняет сетевые запросы во время обращения Dashboard.
SQLite, локального индекса, backfill и сохранённых снимков нет. Существующие
маршруты v1 по-прежнему используют прежний кэш в памяти.
[OpenAPI 3.1](openapi-search.json).

```sh
curl -sS http://localhost:8080/v2/deals/search \
  -H 'Content-Type: application/json' \
  --data '{"hosts":["gonka1hvk3t5c4hzn0q8q3lvg6l7k4dfvfa5xqj4a66m"],"limit":50}'
```

Для покупок передайте `buyers` вместо hosts. Внутри каждого массива OR,
между непустыми массивами AND. Адреса сортируются и дедуплицируются.
Отсутствующий/пустой массив не ограничивает соответствующее поле, но **хотя бы
один фильтр должен быть непустым**. Запрос общего реестра через search отклоняется.
Для общего списка остаётся `GET /v1/deals` с прежним контрактом.

Максимум 100 адресов в каждом массиве до дедупликации, limit 1…100 (default 50),
JSON-тело до 32 KiB. Адреса проверяются по Bech32 checksum, префиксу gonka,
нижнему регистру и длине 20/32 байта. Null вместо массива, неверный тип элемента
и неизвестные поля — ошибка всего запроса. Опечатка `host` не расширяет выдачу.

## Источник данных и проверка принадлежности

- Без buyers: `tx_search` по `wasm-offer_created.host` и emitter нашей Factory.
- С buyers: `tx_search` по `wasm-deal_funded.buyer`; hosts отбираются по атрибуту
  события и повторно сверяются с config сделки.
- Проверяется успешность транзакции и единственный emitter/атрибуты. Sender
  транзакции, плательщик комиссии и reward recipient не являются фильтрами.
- Для покупок ID восстанавливается отдельным поиском события создания этой
  сделки нашей Factory. Для хостов ID уже содержится в событии создания.
- ID и адрес сверяются через Factory `deal { id }`. Только затем читаются
  config/state найденной сделки; config.factory и config.deal_address проверяются.
- Buyer берётся из текущего state, а не из отправителя транзакции. Непустой
  buyers исключает buyer:null. Статусы не ограничиваются.

Обхода `list_deals` и запросов деталей всех контрактов при поиске нет. Примерно
3 дополнительных smart queries на найденного кандидата host и 4 сетевых
запроса на кандидата buyer, включая подтверждение события создания. Чужие
контракты и чужие emitters в результат не включаются.

## Ответ и пагинация

Ответ включает полные детали из текущего v1 API: строковые ID/epoch/суммы,
address, host, buyer, status, factory, settlement_cw20 и freshness-поля.
Дополнительно:

```json
{
  "deals": [],
  "next_cursor": null,
  "search_height": "6734586",
  "source": "chain",
  "consistency": "live_state",
  "history_completeness": "unknown",
  "partial_page": false,
  "updated_at": 1792954800,
  "stale": false
}
```

`search_height` — верхняя граница поиска **событий**, закреплённая при первом
запросе. Новые события выше неё появятся после нового поиска без cursor.
Config/state читаются текущими: это **не снимок состояния на этой высоте**.
`updated_at` — Unix seconds начала текущего запроса; stale=false означает
успешное чтение в этом запросе, но не подтверждает возраст последнего блока.
Нода с catching_up=true или выключенным индексом транзакций отклоняется.

Порядок: нормализованные кошельки, внутри каждого — транзакции от новых к старым
и исходный порядок событий транзакции. При наличии buyers обходятся покупатели,
иначе хосты. Это не глобальная сортировка по deal ID. Для одного connectedWallet
показываются сначала новые создания/финансирования.

Cursor содержит параметры, высоту и позицию в выдаче ноды. Он не хранится на
сервере, не подписан и не является security token или гарантией неизменности
выборки. Значения проверяются до использования; cursor другого фильтра/limit —
400 INVALID_CURSOR. Перестановки и дубли адресов допустимы. Самостоятельно
конструировать или менять cursor клиенту не следует.

На одну попытку разрешено до 256 запросов поиска/деталей плюс один status
и до 1000 просмотренных событий. При достижении бюджета возвращается
`partial_page:true` и next_cursor — страница может содержать меньше limit
записей или быть пустой. Dashboard продолжает по next_cursor, а не по длине
массива. next_cursor:null означает конец доступной выдачи индекса ноды.
Таймаут всего запроса — 30 секунд, каждого сетевого запроса — 10 секунд.
Одновременно выполняется максимум 8 поисков на процесс.

В [режиме пула](node-pool.md) добавляется проверка chain ID, свежести блока и
индекса. Новый поиск повторяется целиком максимум на трёх узлах, по 12 секунд
на попытку в пределах общего таймаута. Курсор дополнительно закрепляет origin:
продолжение не переключается на другую историю при сбое. Старый курсор без
origin или курсор исключённого из конфигурации узла — `INVALID_CURSOR`;
недоступный закреплённый узел — `MONITORING_UNAVAILABLE`. Начните поиск заново
без курсора. Бюджет запросов/событий применяется отдельно к каждой попытке.

## Ограничения сетевого варианта

Полнота истории неизвестна: публичная нода может не хранить старые события.
Пустая выдача не доказывает отсутствие сделок во всей истории сети.
Несогласованные страницы, изменившийся total_count, повтор хеша внутри страницы,
ошибки RPC и деталей возвращают 503; частичный успешный ответ при ошибке не выдаётся.

Изменение состояния между страницами, переиндексация и откат сети могут менять
результат. Фиксация верхней высоты уменьшает сдвиги от новых транзакций, но не
заменяет snapshot. При ошибке истории клиент может начать поиск заново.
Гарантий снимка на 15 минут и p95 из первоначального ТЗ у этого варианта нет.
Результаты прежнего SQLite benchmark к нему неприменимы и удалены.

| HTTP | error.code |
| --- | --- |
| 400 | INVALID_FILTER / INVALID_LIMIT / INVALID_CURSOR |
| 413 | REQUEST_TOO_LARGE |
| 429 | RATE_LIMITED, Retry-After: 1 |
| 503 | MONITORING_UNAVAILABLE |

Формат ошибок: `{"error":{"code":"…","message":"…","field":"…"}}`;
field присутствует для параметров запроса. Нет скрытого fallback на общий реестр.
При смене/отключении кошелька Dashboard сбрасывает страницы и cursor.

## Запуск и проверки

Существующие `GONKA_REST_URL` и `GONKA_RPC_URL` должны указывать на одну сеть.
Новых env-переменных или файлов БД не требуется. Старая временная SQLite,
если осталась от прежней реализации, этим кодом не читается и не изменяется.

`./scripts/check` выполняет форматирование, Clippy и тесты. Сетевые тесты используют
локальные mock REST/RPC: фильтры OR/AND, buyer:null, пагинация транзакций/событий,
нормализация cursor, поддельные emitters, чужая Factory, ошибки/неполные страницы,
ограничение работы с продолжением. Также проверяется отсутствие list_deals
и обращений к ноде при невалидном запросе. Старые проверки v1 сохранены.

## Результат проверки 2026-10-26

`./scripts/check`: форматирование, Clippy и 27 тестов прошли. На живой pilot
Factory прямые запросы hosts=[H], buyers=[B] и их AND вернули сделку 1;
переставленные роли — пустой список, отсутствие фильтров — 400.
Время одиночных успешных проверок — 0,64…0,73 секунды, это smoke, не нагрузочный
SLA. [Ответы сетевой проверки](research/network-search-smoke.json).
Локальный проверочный процесс остановлен; production-деплой не выполнялся.
